# UC12: a second account of the same provider (real accounts)

**Spec §11 UC12.** The user adds a second Claude account (or the API-credit pool of the same plan)
as an opt-in external provider. From a Claude Code client, delegable tasks may go to that account.
**Verifica:** the invariant "the host does not invoke itself" holds for the account of the session,
not for the second one.

Automated twin: `test/e2e/uc12.test.ts` (fake `claude`, both directions, the child's
`CLAUDE_CONFIG_DIR`). This script proves a real second login really is a separate account and
quota, and that Claude Code's own `CLAUDE_CONFIG_DIR` handling matches what Dispatch assumes.

> **Terms.** Driving a second consumer subscription non-interactively is a grey area of Anthropic's
> usage rules. Read the README billing disclosure before enabling `claude-alt`. Dispatch applies no
> technical workaround and never touches either login.

## Prerequisites

- [UC1](UC1.md) done (`dispatch setup`, plugin enabled).
- Two Claude accounts: your normal one (logged in under `~/.claude`) and a second one you are
  willing to spend a few requests on. For the API-credit variant, a Console/API login in its own
  config dir instead of a second subscription.
- A scratch repo (`~/dispatch-scratch/uc12`, `git init`, one small source file, `dispatch install`).

## Steps

### 1. Log in the second account in its own config directory

You do this; Dispatch never does and never reads the result.

```sh
mkdir -p ~/.claude-alt
CLAUDE_CONFIG_DIR=$HOME/.claude-alt claude        # complete the login in the TUI, then /exit
```

Check it is a different account: start `CLAUDE_CONFIG_DIR=$HOME/.claude-alt claude`, run `/status`
(or `/usage`) and compare with the default session. Note both usage figures.

### 2. Declare the instance

Add to `~/.dispatch/config.yaml` (keep the other keys):

```yaml
providers:
  claude-alt:
    adapter: claude
    config_dir: ~/.claude-alt        # absolute or ~/...; becomes CLAUDE_CONFIG_DIR of the child
    plan: pro
  # API-credit pool variant (use instead of, or next to, the above):
  # claude-api:
  #   adapter: claude
  #   config_dir: ~/.claude-api
  #   pool: api_credit
```

Then a profile that may use it. Either edit your active profile or create
`~/.dispatch/profiles/accounts.yaml` and run `dispatch use accounts`:

```yaml
version: 1
rules:
  - id: any-claude-account
    action: { type: fallback, instances: [claude, claude-alt], strategy: ordered }
```

```sh
dispatch validate        # Configuration OK
dispatch providers       # claude and claude-alt, both claude adapter
dispatch status          # claude-alt listed with its pool and plan
dispatch doctor          # the claude-alt checks are ok (login state: unknown is expected)
```

### 3. From a session on the default account: the second account is a valid target

```sh
cd ~/dispatch-scratch/uc12 && claude                 # default account (no CLAUDE_CONFIG_DIR)
```

`dispatch status` (any terminal started from that session, or in the session via `!`) marks
`claude` as the host: `(host — interactive usage not visible)`. Ask Claude:

> Delegate to Dispatch: review src/<file> and list any bugs. Use the dispatch sub-agent.

(The `any-claude-account` rule is a fallback in the order `claude`, `claude-alt`: the router skips
`claude` because it is the host.) Expected:
- The result names `claude-alt` as the instance.
- `dispatch logs --task <runId>` shows the decision: `claude: filtered: self (the host never
  delegates to itself)` and `claude-alt` kept.
- In the second account's own session, `/usage` (or the account page) shows a few more requests than
  in step 1; the default account's usage is unchanged by Dispatch (interactive use aside).

Try the invariant directly from inside the session:

```sh
dispatch run --provider claude --task 'say hi' --json
```

Expected: `"status": "returned_to_host"` with a summary saying `claude was filtered out` and **no**
Claude process is started for it (the host never invokes its own account).

### 4. From a session on the second account: the roles swap

```sh
cd ~/dispatch-scratch/uc12 && CLAUDE_CONFIG_DIR=$HOME/.claude-alt claude
```

`dispatch status` now marks `claude-alt` as the host and `claude` is a valid target. Delegate a task
the same way. Expected: the instance is `claude` (the default account), the decision shows
`claude-alt: filtered: self`, and the usage moves on the default account.

### 5. Pool visibility (if you configured `claude-api`)

`dispatch status` shows `pool api_credit` for it. Delegating to it spends API credit, not
subscription quota: check the Console usage page.

## Pass criteria

- Steps 3 and 4: the delegated task runs on the other account, never on the session's own, and the
  usage numbers moved on the expected account only.
- The direct `--provider claude` from the default session is refused without spawning.

## Cleanup

Remove the `claude-alt` (and `claude-api`) lines and the `accounts` profile, `dispatch use balance`,
`dispatch uninstall` in the scratch repo, and `rm -rf ~/dispatch-scratch/uc12`. Log out of the second
account with `CLAUDE_CONFIG_DIR=$HOME/.claude-alt claude` then `/logout` if you do not need it, and
delete `~/.claude-alt`.
